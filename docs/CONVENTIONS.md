# AskMate 협업 컨벤션

## 1. 기준과 적용 범위

이 문서는 브랜치, 커밋, Issue, Pull Request(PR), 리뷰 및 개발 환경의 공통 규칙을 정리한다.
과제 필수 조건은 과제 본문을 기준으로 하고, 구체적인 역할과 작업 흐름은 `plan.pdf`를 따른다.
문서에 추가한 명명 규칙, 리뷰 승인 기준, 병합 방식은 이번 PR에서 팀이 검토할 운영 규칙이다.

| 구분 | 내용 |
| --- | --- |
| 과제 필수 | 브랜치 전략, 기능 단위 작업 이력, PR 기반 Merge 기록 |
| 과제 필수 | 팀원별 유의미한 커밋 최소 10회, 역할과 개인별 작업 요약 문서화 |
| 기획서 선택 | `main`은 배포 기준, `develop`은 통합 기준, 작업 브랜치에서 개발 |
| 기획서 권장 | 팀원별 PR 최소 3개, 다른 팀원 PR 리뷰 최소 2회 |
| 이번 운영 규칙 | PR마다 작성자 외 팀원 1명 이상의 승인, Merge commit 방식 사용 |

커밋 수는 프로젝트 전체 기간의 기준이다. 횟수를 채우기 위한 빈 커밋이나 불필요한 분할은 하지 않는다.
규칙 변경도 문서 수정 PR로 제안하고 리뷰 후 반영한다.

## 2. 역할과 협업 경계

| 팀원 | 주요 역할 |
| --- | --- |
| A | 백엔드 구조·공통 설정·인증·접근 제어, D의 DB·조회 설계와 리뷰 지원, develop 통합 |
| B | AI API·최근 대화 문맥·예외 처리·운영 로그·배포, C의 채팅 연동 지원 |
| C | 회원가입·로그인·채팅 화면, 입력 검증과 로딩·오류 표시 |
| D | 대화 기록 API·화면·확인용 SQL, 테스트와 API·DB 문서 |

A의 백엔드 리드 역할은 팀장 직책을 의미하지 않는다.
모든 팀원이 자신의 기능에 필요한 검증·문서·PR에 참여한다.
지원은 설계 안내와 PR 리뷰를 중심으로 하며, 공통 파일이나 API 규격 변경은 관련 담당자와 먼저 조율한다.

## 3. 브랜치 규칙

```text
최신 develop → 작업 브랜치 → develop 대상 PR → 팀원 리뷰 → Merge
develop → main 대상 PR → 통합 확인·팀원 리뷰 → Merge
```

- `main`: 검증된 배포 기준을 유지한다. 직접 작업하거나 직접 push하지 않는다.
- `develop`: 완료된 작업을 통합한다. 기능 변경은 PR로 받는다.
- 작업 브랜치: 하나의 명확한 작업 범위를 담당하며, 최신 `develop`에서 생성한다.
- 작업 브랜치는 완료·검증·리뷰 후 `develop`에 병합한다.
- `develop`은 팀이 정한 배포 범위가 완성되고 함께 정상 동작할 때 `main`에 병합한다.
- 병합 기준은 모듈 개수나 패키지 크기가 아니다. 초기 구성도 첫 안정된 기준으로 병합할 수 있다.
- 병합이 끝난 작업 브랜치는 삭제하고, 다음 작업은 최신 `develop`에서 새로 시작한다.
- `main`과 `develop`은 계속 유지한다. 공유 브랜치의 이력을 강제로 덮어쓰지 않는다.

### 브랜치 이름

`<유형>/<짧은-영문-작업명>` 형식으로 쓰며, 작업명은 소문자와 하이픈을 사용한다.

| 접두어 | 용도 | 예시 |
| --- | --- | --- |
| `feature` | 새 기능 | `feature/auth` |
| `fix` | 오류 수정 | `fix/history-user-filter` |
| `docs` | 문서·협업 양식 | `docs/collaboration-conventions` |
| `chore` | 환경·의존성·도구 설정 | `chore/backend-bootstrap` |
| `refactor` | 동작을 유지하는 코드 구조 개선 | `refactor/auth-dependencies` |
| `test` | 테스트 추가·개선 | `test/auth-access` |

접두어는 작업 성격을 나타낸다. `chore`는 여러 모듈을 모아두는 통합 브랜치가 아니다.

### 작업 시작 예시

아래 명령은 원격 `develop`이 생성되어 있고 현재 변경사항이 정리된 상태를 전제로 한다.

```bash
git switch develop
git pull --ff-only origin develop
git switch -c feature/auth
```

최초에는 `main`에서 `develop`을 만들고, 그 위에서 초기 작업 브랜치를 생성한다.
이번 문서 작업 브랜치는 `docs/collaboration-conventions`이며, 백엔드 초기 구성은 이후 `chore/backend-bootstrap`에서 진행한다.

## 4. 커밋 규칙

형식은 `<유형>: <변경 내용>`이며 설명은 한국어 또는 영어로 작성한다.
유형은 `feat`, `fix`, `docs`, `chore`, `refactor`, `test`를 사용한다.
브랜치 접두어 `feature`에 대응하는 커밋 유형은 `feat`이다.

```text
chore: backend uv 프로젝트와 실행 의존성 구성
feat: 회원가입 API 추가
fix: 다른 사용자의 대화 기록 조회 차단
docs: 로컬 실행 방법과 환경 변수 설명 추가
```

- 하나의 커밋은 설명 가능한 변경 단위로 구성한다.
- 구현, 검증, 문서화, 리뷰 반영의 실제 작업을 이력에 남긴다.
- 커밋 전 staged diff를 확인하고, 관련 없는 변경이나 민감정보가 포함되지 않도록 한다.

## 5. Issue 규칙

- 작업 전에 기존 Issue를 확인하고, 기능·오류·문서·환경 작업을 설명할 Issue를 작성한다.
- 제목은 `feat: 회원가입 구현`, `docs: 협업 규칙 정리`처럼 작업 목적을 드러낸다.
- `Summary`에는 해결할 문제나 목표, `Description`에는 작업 범위와 배경을 적는다.
- 완료 조건을 체크리스트로 적고, 오류라면 재현 순서·기대 동작·실제 동작을 포함한다.
- 담당자는 GitHub Assignees로 지정하고, 관련 Issue·PR이 있으면 번호를 기록한다.
- 라벨은 저장소에 실제 등록된 항목 중에서 선택한다. 템플릿은 라벨·담당자를 자동 지정하지 않는다.

## 6. PR 작성과 리뷰

- 일반 작업 PR의 base는 `develop`, compare는 자신의 작업 브랜치로 지정한다.
- 배포 기준을 갱신하는 PR은 base를 `main`, compare를 `develop`로 지정한다.
- GitHub가 기본 브랜치를 base로 선택할 수 있으므로 PR 생성 시 대상을 확인한다.
- PR 제목은 커밋과 같은 `<유형>: <변경 내용>` 형식으로 작성한다.
- 본문에는 목적, 변경 내용, 관련 Issue, 검증 방법과 결과, 리뷰가 필요한 부분을 적는다.
- 검증하지 못한 항목은 이유와 함께 명시한다. 문서만 바꿨다면 문서 확인 내용을 적는다.
- 미완료 작업은 Draft PR로 공유할 수 있다. 완료 후 리뷰를 요청한다.
- 작성자 외 팀원 1명 이상의 승인을 받고, 수정 요청과 필요한 검증을 해결한 뒤 병합한다.
- 리뷰는 담당 기능과 연결되는 동작, 과제 조건, 이해하기 쉬운 구조를 중심으로 한다.
- `develop → main` PR에는 포함된 작업 PR과 통합 검증 결과를 정리한다.

### 병합 방식과 이슈 종료

개인별 유의미한 커밋과 통합 지점을 보존하기 위해 두 단계 모두 GitHub의 **Create a merge commit** 방식을 사용한다.
Squash and merge는 여러 커밋을 하나로 합치므로 이 프로젝트의 기본 병합 방식으로 사용하지 않는다.

`develop` 대상 PR에는 `Related to #번호`로 이슈를 참조한다.
`main`을 기본 브랜치로 운영할 때, `develop` 대상 PR 본문의 `Closes #번호`는 자동 종료에 사용되지 않는다.
팀은 이슈를 `main` 반영까지 열어두고, `develop → main` PR 본문에 완료된 이슈별로 `Closes #번호`를 작성한다.
부분 완료 이슈에는 종료 키워드를 사용하지 않는다.

저장소 관리자는 가능하면 `main`·`develop`에 PR과 승인 리뷰를 요구하는 보호 규칙을 설정한다.
문서만으로 GitHub 설정이 적용되는 것은 아니며, Merge commit을 허용하는 설정과 함께 확인해야 한다.

## 7. 백엔드 개발 환경 규칙

다음은 이후 백엔드 초기 구성에서 구현할 기준이며, 이 문서 PR이 서버를 추가하지는 않는다.

- FastAPI 서비스와 Python 프로젝트 설정은 `backend/`에 둔다.
- `backend/pyproject.toml`과 `backend/uv.lock`을 함께 버전 관리한다.
- 팀 공통 Python 버전은 초기 구성 시 정하고 `.python-version`과 README에 기록한다.
- 의존성 추가는 `backend/`에서 `uv add <패키지>`, 설치는 `uv sync`로 수행한다.
- 실행 명령은 `uv run`을 사용하며, 실제 진입점과 명령은 초기 구성 후 README에 기록한다.
- `.venv`, Python 캐시, 실제 `.env` 및 실행 중 생성되는 DB·로그는 Git에 올리지 않는다.
- 환경 변수를 도입하면 `.env.example`에 변수 이름과 비밀이 아닌 예시 값을 기록한다.
- 인증 방식, AI 제공자, DB 모델 등 기능 설계는 해당 작업에서 관련 팀원과 정한다.

## 8. GitHub 템플릿 위치와 활성화

| 용도 | 저장 위치 |
| --- | --- |
| Issue 선택 화면의 Markdown 템플릿 | `.github/ISSUE_TEMPLATE/task.md` |
| 새 PR 본문의 기본 템플릿 | `.github/pull_request_template.md` |

제공된 기존 양식의 `Summary`와 `Description`을 유지하고, 작성 안내는 HTML 주석으로 바꿨다.
Issue에는 GitHub가 선택 화면에서 사용할 YAML front matter의 `name`과 `about`을 추가했다.
Markdown Issue 템플릿은 현재도 지원되므로 YAML Issue Forms로 전환할 필요는 없다.

템플릿은 **저장소의 기본 브랜치에 반영된 뒤** 사용할 수 있다.
이 프로젝트는 `main`을 기본 브랜치로 두는 것을 기준으로 한다.
따라서 이번 템플릿은 작업 브랜치나 `develop`에만 있어서는 활성화되지 않는다.
초기 PR들은 양식 내용을 직접 복사해 작성하고, 리뷰 후 `develop → main`까지 병합한다.
이후 새 Issue 작성 화면과 새 PR 작성 화면에서 표시 여부를 확인한다.
Issue 기능이 꺼져 있다면 저장소 관리자가 활성화해야 한다.
